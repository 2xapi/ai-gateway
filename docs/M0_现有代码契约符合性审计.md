# M0 现有代码契约符合性审计

> 审计对象：`~/Documents/Codex/2026-08-13/2xapi-tauri/src-tauri/src/`（8 个 Rust 模块，已编译出 14.5MB 二进制）
> 审计基准：`docs/01` §4 行为矩阵 + §6 D1~D7、`docs/02` 数据模型、`docs/04` 接口
> 性质：**只读审计**，不改任何代码。产出 = 偏差清单 + evolve/greenfield 取舍依据。
> 日期：2026-08-13

---

## 0. 一句话结论

> 现有代码是一份**「无网关、仅 PureApi、直接改写 config.toml」**的简化实现；
> 冻结契约要求的是**「内置 axum 网关(:8787) + 三模式 + 协议转换 + 热切换」**的完整架构。
> **两者架构地基不同。** 契约的 centerpiece（本地网关）在现有代码中完全不存在。
> 粗估：现有代码覆盖契约约 **25%~30%**，且可复用的是骨架（Tauri+axum 装配、TOML 原子写、2xapi 登录、probe），核心功能需新建。

---

## 1. 核心架构偏差（最关键）

| 偏差 | 现有代码 | 契约要求 | 影响 |
|---|---|---|---|
| **本地网关** | ❌ 完全没有 `/v1/*` 反向代理；`server.rs` 只有 `/api/*` 管理路由 + 静态前端 | ✅ axum 网关监听 `127.0.0.1:8787`，转发/转换/注入 key（04 §2） | 整个 Mixed/PureApi 经网关的数据流不存在 |
| **config 里 base_url 指向** | `config.rs:91` 把 `custom.base_url` 设为**上游地址**（`provider.base_url`），让 Codex 直连上游 | 契约 02 §5.2：`custom.base_url = http://127.0.0.1:8787`（指向网关） | Codex 绕过网关直连上游 → Mixed 模式根本无法工作（无处注入第三方 key 同时保留 OAuth） |
| **网关端口** | `main.rs:27` 绑定 `127.0.0.1:0`（**随机端口**） | 契约：固定 `:8787` | 即便有网关，config 里写死 8787 也对不上 |
| **热切换零重启** | apply 改 config.toml + auth.json，Codex 需重启读取 | 契约 D7：热切换只影响下一个请求，进行中不中断 | 「零重启」承诺无法兑现（依赖网关持有 active provider） |

> 这条决定了 Q2（evolve vs greenfield）的答案：**网关必须从零新建**，无论选哪条路。区别只在「骨架代码要不要保留」。

## 2. D1~D7 决策逐条符合性

| ID | 决策要求 | 现状 | 判定 |
|---|---|---|---|
| **D1** | Official 不走网关，Codex 直连官方；有 activate-official 切回 | `apply_provider` **永远写 `model_provider="custom"`**（`config.rs:95`），**无 Official 分支**，函数连 access_mode 参数都没有；**无 activate-official 端点** | ❌ 严重不符 |
| **D2** | config.toml 不设 `experimental_bearer_token` | `apply_provider` 确实没写该字段（`config.rs:89-94`） | ✅ 符合（顺带达标） |
| **D3** | 网关统一注入 `provider.api_key` | **无网关**，无从注入；当前是把 key 写进 `auth.json`（`config.rs:120`）让 Codex 自带 | ❌ 不符（依赖网关） |
| **D4** | PureApi 切换前备份 `auth.json.official.bak`；activate-official 恢复 | `apply_provider` **直接覆盖** `auth.json` 的 `OPENAI_API_KEY`（`config.rs:114-123`），**无任何 auth.json 备份**（只备份了 config.toml，`config.rs:82`）；**无恢复机制** | ❌ 严重不符（**破坏性操作，官方 OAuth 会被不可逆覆盖**） |
| **D5** | Codex 恒发 Responses；wire_api=ChatCompletions 时网关做双向转换（含 SSE） | **无转换逻辑**；更糟：`apply_provider` **硬编码 `wire_api="responses"`**（`config.rs:92`），**忽略 provider 自身的 wire_api 字段** | ❌ 双重不符 |
| **D6** | Sub2API 本期留字段+接口，返回 stub | Provider 结构**无 sub2api 字段**，**无 fetch-balance 端点** | ⚠️ 缺失（stub 范围，影响小） |
| **D7** | 热切换只影响下一请求 | 无网关，无热切换概念；apply 改文件需 Codex 重启 | ❌ 不符（依赖网关） |

> **关键洞察**：D1/D3/D4/D5/D7 不符的根因是同一个——**网关不存在**。现有代码「能用」仅限「PureApi + 直连上游 + 把 key 塞 auth.json」这一条窄路径，且该路径对官方 OAuth 是**破坏性**的（D4）。

## 6. 对两个待决问题的证据化建议

### Q1：D1~D7 是否认可？
**建议：认可，且认可即「必须修」。** 审计证明现有代码正是在 D1/D3/D4/D5/D7 上**违规**的——尤其 D4（覆盖 auth.json 无备份）是**破坏性**的。这 7 条决策不是锦上添花，是把代码从「能用但危险且架构缺腿」拉到「正确」的最低门槛。
**但需追加一个范围决策**：§4.3 的「2xapi.com 账号登录/key 分组」子系统，契约里没有，要保留还是删除？（建议保留，并在 04 补一节——它是用户获取 key 的现实入口。）

### Q2：evolve 还是 greenfield？
**建议：evolve，但把网关视为 net-new。**
- 无论哪条路，**网关（契约核心）都要从零写**——这是大头。
- evolve 能复用的现实骨架：Tauri+axum 装配（`main.rs`）、TOML 原子读写（`config.rs` 的 read/write_toml）、2xapi 登录（`auth.rs`）、端点探测（`probe.rs`）、前端壳。greenfield 会把这些重写一遍，收益不大。
- evolve 需要的「重构」：① 新建网关模块 + `/v1/*` 路由 + 协议转换；② 重写 config 引擎（base_url 指网关、支持三模式、wire_api 取 provider 值）；③ 补 Provider 12 个字段 + 修枚举序列化/单位/原子写/键名；④ 统一响应信封 + 错误码；⑤ 加 activate/activate-official/auth 备份恢复/preview/diagnose。
- **若选 greenfield**：现有代码可作参考实现，尤其 config.toml 的真实字段形态（`config.rs:88-108`）和 model catalog 格式（`:128-155`）值得参考。

### 隐含的产品级问题（请一并确认）
审计暴露一个根本疑问：**你真的需要网关吗？** 现有 app「无网关、PureApi 直连上游」是能跑的更简架构。网关的全部必要性来自 **Mixed 模式**（保官方 OAuth + 用第三方）+ **热切换零重启** + **协议转换**。若你确实要这三样（契约已写明要），网关就是必需的；若其实只做 PureApi，可大幅简化。**建议维持契约（要网关、要三模式）**——因为你 v2 文档明确要了，但请知情确认这是一笔不小的复杂度投入。
