# 00 开发流程总纲（开发宪法）

> 2xapi Codex Console —— 模型供应商管理系统
> 本文档定义「如何把项目分里程碑交给 API 开发，并保证每个里程碑一次验收通过」。

---

## 0. 本文档的作用

这是项目的**开发宪法**。所有文档（01~07）从本文档派生。API（AI 编程助手）开发者**必须先读本文档**，再读对应里程碑的输入文档，然后才开始实现。

如果你（API）只允许读一份文档，就是这份。

> ⚙️ **运行模式（2026-08-13 调整）**：本项目由 **agent 自驱开发 + 自动测试当 Gate**，不再由人逐里程碑手工验收。
> agent 按里程碑顺序实现 → 写并跑自动化测试（`cargo test`）→ 全绿 + DoD 自检 → 自动产出交付块并进入下一里程碑，**里程碑之间不等人**。
> **人工只在三处介入**：① 契约变更 CCR（见 07 附录A）② M7 最终用户验收 ③ agent 连续失败无法自解。
> 因此下文 §4「Gate」与 §7「交付节奏」已据此重写；统计模块新增内容已同步到 01~06 契约与任务章节。

## 2. 核心原则

| 原则 | 含义 |
|---|---|
| **契约先行** | 数据模型、接口、行为矩阵在编码前冻结，前后端/网关共用同一份契约 |
| **逐段验收** | 项目不一次性交付，按里程碑 M0→M7 逐段做、逐段验 |
| **零返工传递** | 当前里程碑未通过，绝不进入下一个；缺陷在本里程碑内闭合 |
| **证据驱动** | 每个验收点必须有可复现证据（测试输出 / 命令 / 截图），不接受"应该没问题" |
| **去歧义** | 任何含"大约/可能/看情况"的需求，必须在 01/03 里写成确定的输入→预期输出 |

这五条直接对治 AI 开发的三类偏差：需求偏差、一致性偏差、完整性偏差。

## 3. 里程碑划分（M0 ~ M7）

> 粒度原则：每个里程碑都是**独立可验收**的单元，产出可被下一里程碑当作稳定输入。

| ID | 名称 | 范围摘要 | 主输入文档 | 验收 Gate（通过条件，详见 05） |
|---|---|---|---|---|
| **M0** | 环境与脚手架 | Tauri 项目初始化、依赖锁定、目录结构、`providers.json` 存储、网关端口 8787 启动框架 | 02, 04(部分) | `cargo build` + 前端构建通过；空壳 app 可启动；网关监听 8787 健康检查 200 |
| **M1** | 数据层 | `Provider`/`AccessMode`/`ModelConfig` 结构 + `providers.json` 读写 + CRUD 命令 | 02 | CRUD 单测全过；重启后数据持久；字段与 02 契约 **100% 一致** |
| **M2** | Config 写入引擎 | 三模式 `config.toml`/`auth.json` 生成 + 预览 + 应用 + 备份恢复 | 01(行为矩阵), 02 | 三模式生成内容与 02 契约表**逐字段一致**；预览=实际写入；备份可一键恢复 |
| **M3** | 本地网关 | axum 反向代理 + 三模式处理 + Responses↔Chat 转换 + bearer 注入 + per-provider 代理 + 热切换 | 01, 04(`/v1/*`) | 三模式转发正确（mock 上游验证）；热切换零重启生效；协议转换 round-trip 一致 |
| **M4** | 后端 API 路由 | Provider 管理、使用统计路由 + 网关路由接线 | 04 | 每个路由请求/响应与 04 schema 一致；**错误分支齐全** |
| **M5** | Provider Doctor | probe 增强 + diagnose 三步（配置校验→连接→真实请求） | 03(诊断), 04(diagnose) | 三步顺序执行；返回结构与契约一致；404 自动重试 `/v1` |
| **M6** | 前端 UI | 供应商管理 + 使用统计页 + 首页今日摘要 + 可选透明悬浮窗 + config 预览 + 诊断面板 + api-client | 06 | 三模式 UI 联动后端正确；CRUD、统计入口、悬浮窗和统计状态完整 |
| **M7** | 集成与验收 | 三模式端到端 + 真实 provider 联调 + 交付物整理 | 全部 | 三模式 E2E 用例全过；交付物清单齐全；用户验收 checklist 全勾 |

**依赖链**：M0 → M1 → M2,M3（可并行）→ M4 → M5,M6（可并行）→ M7

## 4. 验收 Gate 规则（自动测试为 Gate）

> ⚙️ **新模式**：Gate = 自动化测试。agent 自驱跑 `cargo test`，全绿 + DoD 自检即自动通过并进入下一里程碑；**里程碑之间不再等人工签字**。

### 4.1 通过条件（agent 自检，全部满足即自动通过）
1. 该里程碑的自动化测试（`cargo test`）**全绿**；
2. 05 中该里程碑所有任务的 DoD 逐条自检打勾；
3. 交付块三件齐全（变更清单 + 自检 + 证据，见 §5 纪律 7）；
4. 无 P0/P1 缺陷（P0=崩溃/数据丢失/契约违背；P1=核心功能不可用）。

### 4.2 证据要求（agent 自动产生并随交付块留档）
- 后端：`cargo test` 实际输出片段；需要 `curl` 的验证一律写成集成测试（headless 自动跑，不依赖人手敲）；
- 网关：mock 上游集成测试 + 转发报文断言；
- 前端：M6/M7 的关键交互截图（此处需人工协助采集，属 4.4 介入点）。

### 4.3 失败处理（agent 自闭环）
- 测试红 → agent 在当前里程碑内修复 → 重跑，**不进下一里程碑**；
- 同一里程碑连续 2 次失败 → 触发【契约复审】（此时才需人工，见 §6）。

### 4.4 人工介入点（仅三处）
① 契约变更 CCR（02/04/01 矩阵要改，见 07 附录A）；
② M7 最终用户验收（05 末尾 10 项 checklist）；
③ agent 连续失败或遇契约歧义无法自解。
其余全部由 agent + 自动测试推进，**不暂停等人**。

## 5. AI 协作纪律（强制，违反即视为交付不合格）

1. **契约冻结** —— 02 数据模型、04 接口、01 行为矩阵是冻结契约，实现必须逐字段匹配。发现契约有缺陷：**停止实现**，发起「契约变更请求 CCR」（格式见 07 附录），待确认后**先改契约文档再实现**。
2. **单里程碑闭合** —— 当前 Mx 未通过验收前，不得读取或实现 Mx+1 的内容。
3. **DoD 自检** —— 提交前逐条对照 05 的 DoD，未达项必须修复，**不得自我标记完成**。
4. **错误分支必填** —— 每个接口/网关路径必须覆盖：超时、401/403、网络不可达、协议不兼容、上游 4xx/5xx。**禁止只写 happy path**。
5. **依赖白名单** —— 只允许引入 02/04 指定的依赖（axum、reqwest、serde、serde_json、toml、tower、tokio 等）。新增依赖必须在 CCR 中说明理由。
6. **代码风格** —— Rust 用标准惯用法 + 中文注释说明业务意图；前端模块化；命名与契约字段对齐（Rust snake_case ↔ JS camelCase 在边界显式映射，不得隐式）。
7. **证据随交付** —— 每个里程碑交付必须含三件：①变更文件清单 ②自检报告（DoD 打勾表）③可复现证据。**三者缺一视为未完成**。
8. **不擅自扩展** —— v2 文档 / 03 未列出的功能一律不做；冒出的"完善建议"记入 08 建议池，**不得混入当前实现**。

## 6. 回退与修复流程

```
验收
 ├─ 全部通过 ──────────────────────────────────────► 进入 Mx+1
 ├─ 局部不通过（<30% 项失败）
 │     └─ API 在当前 Mx 内修复 → 重交失败项 → 复核 → 通过则进 Mx+1
 ├─ 整体不通过（≥30% 项失败）
 │     └─ 回滚到 Mx 起始状态 → 整段重做 → 重新验收
 └─ 同一 Mx 连续 2 次不通过
       └─ 触发【契约复审】：人与 API 共同定位
            是契约歧义？→ 改契约(CCR) → 重做
            是实现偏差？→ 缩小任务粒度 → 重做
```

## 7. 交付节奏（agent 自驱 + 自动测试为 Gate）

> ⚙️ **新模式**：agent 自驱实现 → 跑 `cargo test` → 全绿 + DoD 自检 → 自动产出交付块 → **直接进入下一里程碑，里程碑之间不等人**。人工仅在 CCR（契约变更）/ M7 最终验收 / agent 连续失败无法自解 时介入。下方旧图保留备查。

```
人（驱动方）                          API（实现方）
   │
   1. 从 07 取当前 Mx 的 prompt 模板
   2. 连同相关契约文档章节一起喂给 API ──►
   │                                   3. 按 §5 纪律实现
   │                                   4. 逐条对照 05 的 DoD 自检
   │                                   5. 产出交付块（变更清单+自检+证据）
   │ ◄── 6. 提交交付块
   7. 对照 05 的 Mx DoD + 07 验收 checklist 验收
   ├─ 通过 ──► 进入 Mx+1
   └─ 不通过 ──► 走 §6 回退流程
```

---

## 8. 一句话总结

> **契约冻结在前，任务原子化在中，逐段验收在后，证据随交付闭环。**
> 做到这四点，"一次验收通过"就是默认结果，而不是运气。
