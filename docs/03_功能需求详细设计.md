# 03 功能需求详细设计

> 每条需求都是**可测试的输入→预期输出**。编号 `FR-x.y` 供 05 任务清单与验收引用。
> 实现时不得遗漏任何一条的「错误/边界」子项。

---

## FR-1 供应商管理（CRUD）

| 编号 | 需求 | 输入 | 预期输出 |
|---|---|---|---|
| FR-1.1 | 新建 provider | 合法 Provider 字段 | 写入 providers.json，返回完整对象（含生成的 id/created_at/sort_index） |
| FR-1.2 | 字段校验 | 缺 base_url（非 Official）/ key 非法 | 返回 422 + 字段级错误（见 02 §2） |
| FR-1.3 | 列表查询 | — | 按 sort_index 升序返回全部；标注 active |
| FR-1.4 | 编辑 | id + 部分字段 | 合并更新，返回新对象；不改变 id/created_at |
| FR-1.5 | 删除 | id | 删除；若删除的是 active，active 置 null（不自动切换） |
| FR-1.6 | 排序 | id 列表新顺序 | 重写 sort_index，持久化 |

## FR-2 接入模式切换

## FR-3 Config 写入引擎

| 编号 | 需求 | 输入 | 预期 |
|---|---|---|---|
| FR-3.1 | 生成 config.toml | Provider | 按 02 §5 对应模式生成完整 toml 字符串 |
| FR-3.2 | 生成 auth.json 操作 | Provider(PureApi) | 返回「设置 OPENAI_API_KEY」操作；其他模式返回「不动」 |
| FR-3.3 | 预览 | Provider | 返回将写入的 config.toml/auth.json **全文**，且与实际 apply 结果逐字符一致 |
| FR-3.4 | 应用 | Provider | 原子写入 config.toml（临时文件→rename）；更新 snapshot 字段 |
| FR-3.5 | 备份/恢复 | 见 FR-2.3/2.4 | — |
| FR-3.6 | 不破坏未知字段 | apply 时 | config.toml 中非本应用管理的字段（用户手写的）**必须保留**，仅更新受控字段 |

> FR-3.6 是高风险项：不得用「整体覆盖」实现，必须做「字段级合并」，否则会清掉用户其他配置。

## FR-4 本地网关（127.0.0.1:8787）

| 编号 | 需求 | 输入 | 预期 |
|---|---|---|---|
| FR-4.1 | 健康检查 | `GET /health` | 200 + `{status:"ok", active_provider_id}` |
| FR-4.2 | Official 不走路 | active=null/Official | 网关不参与（Codex 直连）；网关本身仍可 /health |
| FR-4.3 | Mixed 转发 | `/v1/responses` 请求 | 注入 `Authorization: Bearer {provider.api_key}` + `User-Agent`，转发到 `{base_url}/responses`，key 来源=Provider Store（01-D3） |
| FR-4.4 | PureApi 转发 | 同上 | 同 FR-4.3（凭证仍由网关注入，不透传 Codex 带来的） |
| FR-4.5 | Responses 直传 | wire_api=Responses | body 原样转发 |
| FR-4.6 | Chat 转换 | wire_api=ChatCompletions | 请求 Responses→Chat；响应 Chat→Responses（含流式 SSE） |
| FR-4.7 | per-provider 代理 | proxy_url 非空 | 经该代理访问上游 |
| FR-4.8 | 超时 | timeout_secs | 超时返回 504，不挂起 |
| FR-4.9 | 热切换生效 | 切换后下一请求 | 走新 active provider（01-D7）；进行中请求不受影响 |
| FR-4.10 | custom_headers | Provider 有该字段 | 注入到上游请求 |
| FR-4.11 | 错误透传 | 上游 4xx/5xx | 原样返回状态码与 body，不吞错 |

## FR-5 Responses ↔ ChatCompletions 协议转换（FR-4.6 展开）

| 编号 | 需求 | 预期 |
|---|---|---|
| FR-5.1 | 请求转换 | Responses 的 `input`/`instructions` → Chat 的 `messages`；`model`/`stream`/`temperature` 等直映；丢弃无法映射的字段并记日志 |
| FR-5.2 | 非流式响应转换 | Chat `choices[0].message` → Responses 输出结构；保留 usage |
| FR-5.3 | 流式响应转换 | Chat SSE 的 `delta` 事件 → Responses SSE 事件类型映射；正确发送 `response.created`/`response.output_text.delta`/`response.completed` |
| FR-5.4 | round-trip 一致 | 用固定 fixture：Responses 请求 → 转 Chat → mock Chat 响应 → 转回 Responses，关键字段（role/content/finish_reason）一致 |

## FR-6 Provider Doctor 诊断（三步）

> 对应路由 `POST /api/providers/diagnose`。顺序执行，任一步失败仍继续后续步骤并汇总。

| 编号 | 步骤 | 检查内容 | 失败处理 |
|---|---|---|---|
| FR-6.1 | Step1 配置校验 | base_url 合法、api_key 非空（非 Official）、access_mode/wire_api 合法、timeout 范围 | 记入 errors，configValid=false |
| FR-6.2 | Step2 连接测试 | `GET {base_url}/models`（带 key），记录 latencyMs；**404 自动重试 `{base_url}/v1/models`** | reachable=false，保留 latency |
| FR-6.3 | Step3 真实请求 | 按 wire_api 发最小请求（`max_tokens=16`）；Responses→`/responses`，Chat→`/chat/completions` | testOk=false，记错误信息 |
| FR-6.4 | 返回结构 | — | `{ configValid, reachable, latencyMs, models[], testOk, errors[] }`（见 04） |

## 10. 验收要点
