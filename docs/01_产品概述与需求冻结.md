# 01 产品概述与需求冻结

> 本文档把 v2 开发文档**去歧义化**，转化为可测试的冻结契约。
> 重点是 §4 行为契约矩阵、§5 数据流、§6 歧义澄清——这三节是 M2/M3 实现的唯一依据。

---

## 1. 产品概述

| 项 | 内容 |
|---|---|
| 名称 | 2xapi Codex Console —— 模型供应商管理系统 |
| 形态 | Tauri 桌面应用（≈14MB），前端原生 JS/CSS，后端 Rust(axum) |
| 目标用户 | Codex CLI / 桌面端用户，需要在「官方登录」与「多家第三方 API」之间灵活切换 |
| 核心价值 | ① 一处管理多家 provider ② 三种接入模式覆盖所有使用场景 ③ 本地网关做协议转换与诊断 ④ 切换零重启 Codex |
| 技术参考 | 综合 cc-switch、CodexPlusPlus 优点 |

## 2. 术语词典（全文档统一，不得混用）

| 术语 | 定义 |
|---|---|
| **Provider** | 一个上游模型供应商的完整配置（地址、key、模式、模型列表等），见 02 |
| **AccessMode** | 接入模式枚举：`Official` / `Mixed` / `PureApi`，三选一 |
| **WireApi** | 上游协议：`Responses`（OpenAI Responses API）或 `ChatCompletions` |
| **网关 / Gateway** | 内置于应用、监听 `127.0.0.1:8787` 的 axum 反向代理，负责转发、协议转换、key 注入、热切换 |
| **上游 / Upstream** | 网关转发的目标地址，即 `provider.base_url`（官方或第三方） |
| **active provider** | 当前被激活的 provider，网关的所有请求都走它 |
| **UsageStats** | 第三方中转请求的本地用量聚合：Token、请求数、费用、缓存命中率，按日期/provider/模型维度保存 |
| **缓存命中率** | `cache_read_input_tokens / input_tokens`；上游未返回可计算字段时显示“暂无数据”，不得用估算值替代 |
| **UsageOverlay** | 可选的桌面透明用量悬浮窗；与完整使用统计共用 UsageStats，不独立统计 |
| **requires_openai_auth** | config.toml 字段，`true` 表示 Codex 仍使用官方鉴权链路发请求 |
| **experimental_bearer_token** | config.toml 字段，Codex 发请求时携带的 bearer。**本项目决策：Mixed/PureApi 不在此字段注入业务 key**（见 §6 决策 D2） |
| **CCR** | 契约变更请求，发现契约缺陷时发起，格式见 07 附录 |

## 3. 三种接入模式定义

### Official（官方登录）
Codex 使用 ChatGPT OAuth 登录，走 OpenAI 官方 API。不能用第三方 provider。**不经过本地网关**。

### Mixed（保持官登 + 第三方 API）
保留官方 OAuth 登录状态（`auth.json` 不动），同时通过本地网关把请求转发到第三方 provider，由网关注入第三方 key。**兼顾：用第三方模型，但不丢失官方登录/会话历史，可随时切回。**

### PureApi（第三方 API，纯 API）
完全用第三方 API Key，覆盖 `auth.json` 的 `OPENAI_API_KEY`（切换前备份官方值）。官方 OAuth 被替换，需要时从备份恢复。**最干净，完全第三方。**

## 5. 三模式数据流（每跳的认证来源）

```
【Official】不走网关
  Codex ──官方 OAuth token──► https://api.openai.com
  （config.model_provider="openai"，网关不参与）

【Mixed】走网关，官方登录保留
  Codex ──官方 OAuth token──► 网关 127.0.0.1:8787 ──注入 Bearer {provider.api_key}──► {provider.base_url}
  auth.json：不动
  上游协议：按 provider.wire_api 转换（Responses 直传 / ChatCompletions 做转换）

【PureApi】走网关，纯第三方
  Codex ──OPENAI_API_KEY(=provider key)──► 网关 127.0.0.1:8787 ──注入 Bearer {provider.api_key}──► {provider.base_url}
  auth.json：切换前备份官方值 → 写入 provider key
  上游协议：按 provider.wire_api 转换
```

**网关注入原则（D3）**：网关→上游一律使用 `provider.api_key`（单一数据源 = Provider Store），不依赖 Codex 传来的凭证值。

## 6. v2 歧义澄清与本项目决策（冻结）

> 以下每条都是 v2 文档的模糊/矛盾点，已做决策。**API 实现以决策列为准。**

| ID | v2 歧义点 | 本项目决策 |
|---|---|---|
| **D1** | Official 模式 `model_provider="openai"`，但架构图又画网关透传——到底走不走网关？ | **Official 不走网关**。Codex 直连官方。网关仅服务 Mixed/PureApi。架构图中的"透传"分支删除。 |
| **D2** | Mixed 模式 config.toml 写了 `experimental_bearer_token = provider.api_key`，同时网关又注入 bearer——双 source of truth？ | **不在 config.toml 注入业务 key**。key 的唯一注入点是网关（D3）。config.toml 的 `experimental_bearer_token` 字段**省略**。避免两处都可能改 key 导致不一致。 |
| **D3** | PureApi 模式 `auth.json` 已写 key，Codex 会带给网关，网关用谁的 key？ | **网关统一用 `provider.api_key`** 注入上游，不透传 Codex 带来的值。Provider Store 是 key 的唯一真相源。 |
| **D4** | PureApi 切换会覆盖官方 OAuth，怎么恢复？ | **切换到 PureApi 前**，若 `auth.json.official.bak` 不存在则备份当前 `auth.json`；`activate-official` 时从备份恢复。已存在备份则不覆盖（保护最早的官方状态）。 |
| **D5** | Responses↔Chat 转换的方向？ | **Codex 始终发 Responses 格式**。若 `provider.wire_api=ChatCompletions`，网关做 `Responses→ChatCompletions` 请求转换 + `ChatCompletions→Responses` 响应转换（含流式 SSE）。若 `wire_api=Responses` 则直传。 |
| **D6** | Sub2API 的 `sub2api_multiplier` / `fetch-balance` 具体语义？ | 本期**仅留接口与字段**，不实现具体余额逻辑（标记为 stub，返回占位）。M4 路由存在即可，不纳入验收 gate。 |
| **D7** | 热切换时正在进行的请求怎么办？ | **热切换只影响"下一个"请求**。进行中的请求继续走旧 provider 直至完成。不中断、不回滚。 |

## 7. 非目标（明确不做，API 不得自行实现）

- 不做多账号 OAuth 管理（官方登录态由 Codex 自己维护，本应用只读不动，PureApi 例外见 D4）。
- 不实现 Sub2API 的真实余额计算（D6）。
- 不做模型微调/训练相关功能。
- 不内置任何硬编码 API Key；所有 key 来自用户输入并存入 Provider Store。
- 不做云同步/远程管理；纯本地单机。
- 不统计 Official 直连官方请求；使用统计只覆盖经本地网关转发的第三方中转请求。
- 不把本地网关估算的 Token 当作中转站账单数据；费用必须来自上游 usage/计费接口或明确标注为本地估算。

## 8. 第三方中转站使用统计（新增冻结范围）

### 8.1 统计对象与数据来源

- 统计范围：`Mixed` / `PureApi` 激活期间，经 `127.0.0.1:8787` 发往第三方 provider 的请求。
- 不统计：`Official` 直连请求、未经过本地网关的其他客户端请求、登录/探测失败请求的虚构用量。
- 首要数据源：上游响应中的 `usage` 字段；流式响应优先读取最终 usage 事件。
- 可选数据源：中转站提供的用量/账单 API，仅在用户主动配置且接口可用时刷新；不能访问时不影响本地统计。
- 费用字段必须携带 `source`（`upstream` / `local_rate` / `unknown`），页面不得把 `unknown` 显示成精确账单。

### 8.2 统计维度与入口

- 首页顶部账号/余额区域增加今日摘要：今日 Token、缓存命中率、费用，点击进入完整统计页。
- 左侧导航增加「使用统计」，进入完整统计页；两个入口读取同一套数据。
- 完整统计页包含：今日摘要、输入/输出 Token、缓存命中 Token、请求数、费用、历史热力图、时间范围趋势、模型用量排行、中转站筛选。
- 默认筛选当前 active provider；可切换单个中转站或全部第三方中转站。

### 8.3 统计口径

- `total_tokens`：优先使用上游 `usage.total_tokens`，缺失时使用 `input_tokens + output_tokens`。
- `input_tokens` / `output_tokens`：按规范化 usage 字段累计；字段缺失则保留 `null`，不填零掩盖缺失。
- `cache_read_input_tokens`：兼容 `cache_read_input_tokens`、`cache_read_tokens` 等已知字段；无法识别则为 `null`。
- `cache_hit_rate`：有有效 `input_tokens` 与 `cache_read_input_tokens` 时计算，否则返回 `null`，页面显示「暂无数据」。
- 日期按本机时区归档，日界线为本地时间 `00:00:00`；历史数据至少保留 90 天。

### 8.4 隐私与一致性

- 只保存聚合统计，不保存 prompt、响应正文、Authorization、API Key 或 Cookie。
- 每次请求生成内部 `request_id`，响应完成后只落一条聚合增量，避免流式响应重复计数。
- 本地统计与中转站账单可能因折扣、重试、取整存在差异，页面明确显示数据来源与同步时间。

### 8.5 可选透明用量悬浮窗

- 默认关闭：首次安装、升级和启动时均不得强制显示；用户在设置中主动开启后才显示。
- 收起态只显示当前中转站、今日 Token、缓存命中率、今日费用和同步状态；展开态增加输入/输出 Token、请求数、Top 模型和「打开完整统计」入口。
- 使用与首页摘要、完整统计页相同的 UsageStats 数据源，不单独轮询、不重复累计请求。
- 透明度范围 `60%~100%`，默认 `88%`；设置持久化。鼠标移入恢复到 `100%` 是可选行为，默认开启但不改变数据。
- 默认始终置顶为开启，默认鼠标穿透为关闭，避免用户无法点击；鼠标穿透作为高级选项，开启前显示风险提示。
- 支持拖动、收起/展开、隐藏/显示和位置记忆；支持全局快捷键隐藏/显示。关闭悬浮窗不影响网关和统计记录。
- 数据请求失败时保留最近一次成功数据并显示最后同步时间；从未成功时显示「暂无数据」，不得显示原型演示数字。
- macOS、Windows 支持透明窗口；Linux 若能力不足，保留设置入口但明确显示平台不支持，不影响主界面使用。

## 9. 验收要点（本契约如何被检验）

- M2 验收：按 §4 矩阵 15 行，逐行比对三种模式生成的 `config.toml`/`auth.json` 内容。
- M3 验收：按 §5 数据流，用 mock 上游验证每跳的 Authorization 头来源。
- §6 的 7 条决策，每条必须在对应里程碑的自检报告里**显式确认已遵循**。
- §8 的统计边界、缓存命中率缺失处理、流式请求去重和敏感信息不落盘必须有自动化测试。
